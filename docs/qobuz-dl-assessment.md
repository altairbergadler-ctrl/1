# `qobuz-dl` assessment (security / terms / code / dependency audit)

Дата аудита: 2026-08-09. Gate из `docs/music-service-mvp-plan.md` («Security/legal gate: qobuz-dl»)
и `docs/music-service-handoff.md` (п. 6.2). Результат gate: **RESTRICT** — интеграция разрешена
только с ограничениями из раздела 7 этого документа.

## 1. Объект аудита

| Параметр | Значение |
| --- | --- |
| Репозиторий | <https://github.com/vitiko98/qobuz-dl> |
| Артефакт | PyPI-пакет `qobuz-dl==0.9.9.10` (последняя опубликованная версия; зафиксирована в `backend/requirements.txt`) |
| Тип | сторонний CLI/Python-модуль, **не** официальный Qobuz-плагин |
| Лицензия | **GPL-3.0** (`LICENSE` в репозитории) |
| Происхождение кода | `qopy.py`/`spoofer` — модифицированные модули Qo-DL-Reborn (Sorrow446, DashLt) |

Пакет используется **только как библиотека**: импортируются `qobuz_dl.bundle`,
`qobuz_dl.qopy`, `qobuz_dl.downloader`. CLI, интерактивный (`pick`/curses) и
`lucky`-режимы, а также запись `~/.config/qobuz-dl/config.ini` не используются.

## 2. Дерево зависимостей (SBOM)

Прямые зависимости пакета (`requirements.txt` апстрима):

`pathvalidate`, `requests`, `mutagen` (уже есть в проекте, 1.47.*), `tqdm`,
`pick==1.6.0`, `beautifulsoup4`, `colorama`.

`pick` и `colorama` нужны только интерактивному CLI; в серверном пути кода не
вызываются. Новых транзитивных зависимостей с сетевой активностью нет.

## 3. Code review

### 3.1 Авторизация и хранение учётных данных

- `qopy.Client.auth` вызывает `user/login` с параметрами `email`, `password`, `app_id`
  по HTTPS к `https://www.qobuz.com/api.json/0.2/`.
- Пароль передаётся **только в виде MD5-хеша**: CLI апстрима хеширует пароль до
  инициализации клиента (`cli.py`), наш сервис делает то же самое программно.
  Открытый пароль за пределы процесса не уходит.
- Ответ `user_auth_token` кладётся в заголовок `X-User-Auth-Token` сессии `requests`.
- Пароль и токен **не логируются**: в лог попадают только «Logged: OK» и `short_label`
  тарифа. Проверено по всему `qopy.py`, `downloader.py`, `core.py`.
- Наш сервис **не** создаёт `config.ini` qobuz-dl и не передаёт пакету пути к `.env`,
  базе или Docker socket: email/password подаются из `Settings` программно, в БД не
  сохраняются (в отличие от OAuth-токенов Spotify, для Qobuz в `playlist_sources`
  ничего не пишется).

### 3.2 Извлечение app_id/secrets

- `bundle.py` скачивает `https://play.qobuz.com/login` и JS-бандл
  `/resources/<ver>/bundle.js`, извлекает регулярными выражениями `appId` и набор
  seed-секретов, раскодирует их base64. Валидный секрет проверяется тестовым
  запросом `track/getFileUrl` (`qopy.Client.cfg_setup`).
- Это хрупкая точка (смена вёрстки/бандла ломает regex) — митигация: кэш
  `app_id`/`secrets` в Redis с TTL и повторное извлечение только при промахе/ошибке
  `InvalidAppSecretError`.

### 3.3 Скачивание и запись файлов

- `track/getFileUrl` подписывается `md5("trackgetFileUrl" + … + secret)`; CDN-URL
  возвращает Qobuz API. Файлы скачиваются `requests` потоково во временный `.tmp`,
  затем тегируются `mutagen` (`metadata.tag_flac`/`tag_mp3`) и переименовываются.
- Пути санитизируются `pathvalidate.sanitize_filename/sanitize_filepath`.
- **Найденные дефекты апстрима** (не блокеры, учтены в обёртке):
  1. Часть вызовов `requests` без `timeout` (`tqdm_download`, `Bundle`) — риск
     зависшего воркера; митигация: stale-таймаут job (`QOBUZ_DOWNLOAD_JOB_STALE_SECONDS`)
     и последовательная обработка с прогрессом в heartbeat.
  2. `tqdm` прогресс-бары в stdout Celery-воркера — шум в логах, безвреден.
  3. `downloader.Download` глотает часть ошибок тегирования (лог вместо исключения) —
     обёртка верифицирует результат по факту файлов (см. 3.5).

### 3.4 Сетевая карта (allowlist для sandbox)

Исходящие HTTPS только к:

- `play.qobuz.com` (login-страница и JS-бандл);
- `www.qobuz.com/api.json/0.2/*` (API);
- CDN-домены из подписанных `url` ответа `track/getFileUrl` (зона `*.qobuz.com`);
- `static.qobuz.com` (обложки, только если включён embed/cover).

Никаких сторонних/телеметрийных адресов в коде нет.

### 3.5 Проверка результата до импорта в библиотеку

Скачанное **никогда** попадает в `MUSIC_LIBRARY_PATH` напрямую. Поток:
`staging → верификация → перемещение`. Верификация каждого файла: расширение в
allowlist (`.flac`, `.mp3`), `mutagen.File` парсится и имеет ненулевую длительность,
размер > 0, имя санитизировано, целевой путь остаётся внутри `MUSIC_LIBRARY_PATH`
(та же проверка containment, что и в `services/delivery.py`). Конфликты имён не
перезаписывают существующие файлы. Не-аудио артефакты (cover.jpg, booklet.pdf)
остаются в staging и в библиотеку не переносятся.

## 4. Terms / правовой аспект

- Требуется **активная платная подписка Qobuz** (Studio); бесплатные аккаунты пакет
  отклоняет сам (`IneligibleError`).
- qobuz-dl использует недокументированный API веб-плеера; это нарушает букву Qobuz
  API Terms of Use. Проект — личный self-hosted архив для уже оплаченного контента,
  без публичной раздачи; риск блокировки аккаунта несёт владелец. Это осознанное
  ограничение интеграции, зафиксированное здесь явно.
- **GPL-3.0**: репозиторий приватный и не распространяется — обязательств копилефта
  не возникает. При любом будущем распространении сервиса совместная работа должна
  публиковаться под GPL-совместимой лицензией.

## 5. Модель угроз и хранение секретов

| Риск | Оценка | Митигация |
| --- | --- | --- |
| Утечка `QOBUZ_PASSWORD` | высокий impact | только `.env` (gitignored), не пишется в БД/логи, не возвращается API; наружу уходит лишь MD5 по HTTPS |
| Зависший download без timeout | средний | stale-таймаут job, heartbeat, последовательная обработка |
| Хрупкое извлечение app_id/secrets | средний | Redis-кэш с TTL, ошибка → явный `QobuzProviderError`, а не молчаливый retry-шторм |
| Rate-limit/бан Qobuz | средний | один активный qobuz-job, `QOBUZ_MAX_TRACKS_PER_RUN` (по умолчанию 25), пауза `QOBUZ_REQUEST_DELAY_SECONDS` между скачиваниями |
| Подмена/битый файл в библиотеке | высокий impact | staging + верификация mutagen/расширение/размер/containment до перемещения; запись в библиотеку только у `worker` |
| Скомпрометированный пакет | средний | пин `qobuz-dl==0.9.9.10`; пакет не получает `.env`, БД, Docker socket; сеть ограничена доменами Qobuz |
| Избыточные права контейнера | низкий | `backend` монтирует библиотеку read-only как раньше; rw-доступ к библиотеке добавлен **только** `worker` |

Минимально привилегированного способа доступа к Qobuz (OAuth/токен вместо пароля)
не существует — единственный поддерживаемый путь: email + MD5(password). Поэтому
решение — RESTRICT, а не ALLOW.

## 6. Sandbox-тест (подтверждено до интеграции)

- Пакет устанавливается в отдельный venv/образ без доступа к `.env` хоста.
- Все вызовы в тестах замоканы; реальная проверка логина выполняется владельцем
  вручную после заполнения `QOBUZ_EMAIL`/`QOBUZ_PASSWORD`, как и для Spotify/Яндекса.
- Интеграционный путь (fetch-missing → staging → verify → library → scan → match)
  покрыт unit-тестами с сгенерированными FLAC.

## 7. Решение

**RESTRICT** — интеграция разрешена при соблюдении всех ограничений:

1. Пин версии `qobuz-dl==0.9.9.10`; использование как библиотеки (`bundle`/`qopy`/`downloader`), без CLI.
2. Секреты только через env; ничего не сохранять в БД; API никогда не возвращает секреты/токены.
3. Скачивание только в `QOBUZ_STAGING_PATH`; в библиотеку — после верификации и только из `worker`.
4. Один активный qobuz-job; лимит треков за запуск; задержка между скачиваниями.
5. Сеть — только домены Qobuz из раздела 3.4.
6. Любое снятие ограничений (рост лимитов, прямая запись в библиотеку, публикация
   производного кода) — через новый assessment.


## 8. Addendum (2026-08-09): Qobuz OAuth и авторизация токеном браузерной сессии

При live-проверке выяснилось: Qobuz перевёл веб-вход на OAuth-поток, и
классический `user/login` с email + MD5(password) стабильно отвечает **401
Invalid credentials** даже с верной парой (вход через сайт при этом работает).
Пакет `qobuz-dl==0.9.9.10` этот сценарий не покрывает — ровно та хрупкость,
помеченная в разделе 3.2.

**Принятый workaround (в рамках RESTRICT):** авторизация токеном браузерной
сессии. Владелец входит на `play.qobuz.com` в своём браузере; из Local Storage
(ключ `localuser`) извлекаются `token` (user_auth_token) и `id` (user_id) и
записываются в `.env` (`QOBUZ_AUTH_TOKEN`, `QOBUZ_USER_ID`). Сервис
конструирует `qopy.Client` без вызова `user/login`: токен передаётся заголовком
`X-User-Auth-Token`, валидность app-secrets по-прежнему проверяется
подписанным `track/getFileUrl` (`cfg_setup`), тариф считывается через
`user/get`. Проверено вживую: `user/get` → 200 (Studio), `track/search` → 200,
скачивание реального 24/96 FLAC → верификация mutagen → перенос в библиотеку.

Оценка рисков workaround:

- Токен — секрет того же класса, что и пароль: те же меры (только `.env`,
  gitignored, не логируется, не возвращается API, не пишется в БД).
- Токен протухает/ротируется Qobuz. Признак — 400/401 при connect/search;
  восстановление: повторное извлечение из браузера (runbook в README).
- Отзыв доступа: смена пароля/выход из всех сессий на стороне Qobuz инвалидирует
  токен; отдельного отзыва у Qobuz нет.
- Путь email+password сохранён как fallback: если Qobuz вернёт поддержку
  `user/login`, достаточно очистить `QOBUZ_AUTH_TOKEN`.
- Новых сетевых адресов и зависимостей workaround не добавляет; ограничения
  раздела 7 сохраняются в полном объёме.
